# 目标架构与使用差异

## 概述

PTO 的编程模型强调“语义统一、目标有差异”。这意味着文档和 IR 对外提供的是一套稳定的对象模型，但不同目标架构在支持的类型、布局组合、搬运约束和同步要求上可能存在差异。

## 用户如何选择目标架构

当前用户可通过以下方式指定目标：

- `--pto-arch=a3|a5`

建议在编译命令中显式给出目标架构，这样更容易获得稳定且可重复的结果。

## 哪些部分应保持统一

对用户可见的 PTO 编程模型中，下列部分应尽量保持统一：

- 类型系统
- view / tile 对象模型
- 主要操作名与基本语义
- 同步对象与 CV Pipe 语义
- 语法与结构化 IR 组织方式

这保证了：

- 相同 PTO 程序可以在多个目标上共享大部分表达形式
- 相同概念可以在不同目标上保持一致理解

## 哪些部分允许分化

真正可能分化的通常是：

- 某些 op 的支持元素类型集合
- 某些布局 / 位置 / fractal 组合是否合法
- 某些本地数据搬运路径是否可用
- 某些同步或 barrier 的使用要求
- pipe / reserved buffer / workspace 的可用范围

因此，架构差异更多是“同一语义在不同目标上的支持边界不同”，而不是“每个目标都有一套不同语言”。

## 编程模型上的理解方式

写 PTO 程序时，可以把架构说明理解为以下原则：

- 先按统一 PTO 语义表达程序
- 再让编译器告诉你某个实例在目标上是否可接受
- 如果目标需要特殊调整，优先按目标报错或约束调整程序写法，而不是在高层 IR 中提前写入过多目标特化细节

## 6. A3 与 A5 的内存使用差异

两种目标共享 `ptr`、`tensor_view`、`partition_tensor_view` 和 `tile_buf` 对象模型，
但本地数据通路的合法组合不同。以当前公开 TileOp 接口为例：

| 使用点 | A3 | A5 |
| --- | --- | --- |
| 低精度 Tile 元素 | 以 `i8`、`f16`、`bf16`、`f32` 等基础类型为主 | 部分操作额外支持 FP8、HiFloat8 和打包 FP4 |
| `tmov` 的 `vec` → `mat` | 不支持 | 支持 |
| `textract` 的 `vec` → `vec` | 支持基础形式 | 支持 ND 布局（`row_major` + `none_box`） |
| `tinsert` 的目标位置 | `vec` → `vec`、`acc` → `mat` | 额外支持 `vec` → `mat`、`acc` → `vec` |
| `acc` → `mat` 的部分转换 | 目标 `fractal` 需要为 `512` | 无该 `fractal=512` 限制 |

具体元素类型、布局和有效区域以各操作章节的约束为准。
