# 2.1 PTO 机器模型

## 1. 概述

PTO 机器模型定义了 PTO 程序在设备侧所面对的抽象执行环境。它不直接暴露某一代硬件的全部微结构细节，而是把核心、执行部件、片上存储、全局存储和同步资源组织成一套稳定的逻辑对象，供 `PTO ISA`、类型系统和操作语义共同使用。

## 2. 机器层次

PTO 机器模型可以分为三个概念层：

- `Host`：负责编译、准备参数、提交任务与回收结果
- `Device`：负责把 tile 级工作映射到可用执行资源，并维护可观察顺序
- `Core`：负责执行单个 tile 指令序列，是最小的逻辑执行代理

对 `ptoas` 用户而言，最常接触的是 `Device` 和 `Core` 这两层，因为它们直接影响：

- block / subblock 的工作划分
- tile 数据放在哪类局部资源中
- 哪些操作可以并行
- 哪些地方需要同步

但如果从端到端工具链角度理解 PTO，`Host` 也不是背景板，而是任务构造与提交链路中的必要组成部分。

## 3. Host 视角

### 3.1 Host 的职责

在 PTO 机器模型中，Host 负责准备并向设备提交工作。它通常承担以下职责：

- 构造或加载 PTO 程序
- 触发编译、缓存或复用已编译结果
- 准备 kernel 参数与全局内存对象
- 组织 tile 图、任务图或更高层调度单元
- 向一个或多个设备实例提交任务并等待完成

因此，Host 不是直接执行 tile 计算的一方，但它决定了：

- 哪个程序被送去执行
- 程序以什么参数和数据范围执行
- 多个设备任务之间如何组织先后关系

### 3.2 Host 与 PTOAS 的关系

对 `ptoas` 而言，Host 视角主要体现在“PTO 程序如何进入编译链”：

- 通过 `.pto` / `.ptobc` 文本或字节码输入
- 通过 Python / API 构造 `module`
- 通过上层框架把 block 切分、参数和入口函数组织好后再交给 `ptoas`

也就是说，`ptoas` 本身不等于 Host 运行时，但它正处在 Host 准备链路中的关键位置：负责把 Host 提供的程序表示编译成可继续执行或可继续集成的结果。

### 3.3 Host 侧的常见工作

从参考手册角度，可以把 Host 侧常见工作概括为：

- 编译/JIT PTO 程序并缓存结果
- 准备全局张量、工作缓冲区和运行时参数
- 按 block 级粒度切分工作并决定提交形状
- 组织多个 kernel 或多个阶段之间的数据流
- 协调提交、同步与结果回收

这些职责虽然大多不直接写在 `PTO ISA` 中，但会决定：

- `block_idx` / `block_num` 等运行时查询值的意义
- 全局 tensor view 所对应的真实输入输出范围
- 某个函数到底是单独提交，还是属于更大计算图的一部分

### 3.4 Host 不直接承诺什么

PTO 机器模型里的 Host 视角，并不要求文档为每个平台规定统一的宿主 API。它更强调职责边界：

- Host 负责准备和提交
- Device 负责调度和执行
- Core 负责实际 tile 指令流

因此，`PTO ISA` 的重点不是定义宿主侧接口细节，而是定义一套足够稳定的程序对象模型，使 Host 可以把工作可靠地交给后续编译与执行链路。

## 4. Core 视角

### 4.1 标量控制

PTO 机器模型中，core 不只是执行 tile 算子，还包含标量控制能力，用于承担：

- 控制流
- 地址计算
- 事件与同步协调

因此，PTO 程序里的标量 SSA 值与 tile SSA 值并不是两个互不相干的世界，前者通常用于驱动后者的数据选择、视图偏移和执行次序。

### 4.2 逻辑执行部件

从编程模型角度看，一个 core 上通常存在多类逻辑执行部件：

- `cube`：矩阵计算主路径
- `vector`：逐元素、规约、搬运等路径
- `scalar/fix`：控制、辅助计算与部分同步路径
- `memory`：全局与片上之间的数据移动路径

这些名称不要求与底层硬件单元名字逐项一一对应，但在 PTO 中它们对应着明确的语义边界。

## 5. Device 视角

### 5.1 Tile Block

PTO 机器模型中的设备执行不是“一个 kernel 单线程顺序跑完”，而是把工作拆成多个 tile block，再交给设备调度。

每个 tile block：

- 处理一部分输入/输出区域
- 拥有自己的 block 标识
- 可以与其他独立 block 并行执行

### 5.2 Block 与 Subblock

在混合执行模型下，一个逻辑 block 往往不是单一执行体，而是会进一步区分：

- `block_idx`
- `subblock_idx`

其中：

- `block_idx` 通常表示当前逻辑 block 的编号
- `subblock_idx` 通常表示 block 内更细粒度的执行参与者编号

这也是为什么 `pto.get_block_idx`、`pto.get_subblock_idx` 这类运行时查询 op 会直接进入 PTO ISA。

### 5.3 独立 Block 的并行性

如果两个 tile block 之间不存在显式依赖，那么设备可以：

- 并行执行它们
- 乱序执行它们
- 把它们映射到不同 cluster / core 资源上

PTO 对用户真正承诺的不是“固定调度顺序”，而是“可观察语义不被破坏”。

## 6. 存储层次

PTO 机器模型中的存储不是一块统一内存，而是一组具名逻辑域。当前文档中最核心的对象包括：

- `GM`
- `MAT`
- `LEFT`
- `RIGHT`
- `ACC`
- `BIAS`
- `VEC`

这些逻辑域共同决定：

- 数据当前位于哪一层资源
- 哪些搬运路径是合法的
- 哪些计算 op 可以消费该对象
- 哪些读写组合可能引入同步需求

因此，PTO 中的 tile 不是一个脱离资源背景的抽象值，而是始终与机器模型中的位置绑定。

## 7. 数据流路径

从机器模型角度看，PTO 程序通常由三类活动组成：

- 从 `GM` 引入数据
- 在片上局部域之间搬运、重排或保留数据
- 在特定执行部件上消费 tile 并生成结果

典型路径包括：

- `GM -> VEC`
- `GM -> MAT -> LEFT/RIGHT/BIAS`
- `ACC -> GM`
- `VEC -> GM`

这也是为什么 PTO 中的数据搬运操作、局部 tile 类型和布局属性都必须被显式建模。

## 8. 同步资源

PTO 机器模型把同步资源视为一等对象，而不是附加机制。常见同步边界包括：

- pipeline 之间的顺序约束
- block 内不同执行部件之间的依赖
- producer / consumer 之间的 pipe 协调
- 显式 event / flag 所定义的等待关系

因此，设备是否可以并行推进某两段工作，不只取决于文本顺序，还取决于：

- 它们是否访问同一类资源
- 它们是否形成真实数据依赖
- 它们之间是否存在必须满足的同步协议

## 9. 对 PTOAS 用户的意义

理解 PTO 机器模型，主要是为了正确回答以下问题：

- 我的 tile 应该放在哪一类局部对象里
- 我的 block / subblock 如何切分工作
- 我现在写的是数据依赖，还是只是地址重解释
- 我是否需要显式表达 pipe、event 或其他同步对象

如果这些边界不清楚，后续的类型检查、同步推导、地址规划和代码生成都会变得不稳定。
