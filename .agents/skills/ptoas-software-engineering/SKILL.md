# PTOAS 软件设计与编写

让维护者在理解、使用和修改 PTOAS 时少追踪依赖、少记隐含规则。以正常入口的行为和调用方需要知道的信息判断设计成本。

## 触发场景

- 实现新功能、修复缺陷或重构，尤其是涉及 op 语义、Pass 前置条件、后端差异、CLI 或 Python 接口的改动。
- 评审变更时，发现一条规则散落多处、调用方反复做同样的判断，或必须阅读内部实现才能正确调用。
- 按改动使用现有入口。用户可见行为和跨层同步见 [ptoas-project-development](../ptoas-project-development/SKILL.md)，合规和检查门禁见 [enforce-ptoas-code-compliance](../enforce-ptoas-code-compliance/SKILL.md)，测试选型见 [ptoas-test-framework-guidance](../ptoas-test-framework-guidance/SKILL.md)，构建和环境见 [ptoas-development](../ptoas-development/SKILL.md)。

## 设计原则

- **先定位复杂性。** 用三个问题检查受影响的代码。改一条规则要动几处？调用者要掌握多少额外信息？有哪些前提或失败语义只有读实现才会发现？沿实际调用链找出导致这些问题的依赖或模糊契约。
- **用深模块隐藏实现知识。** 给一项语义规则明确归属，优先复用已有 op、类型、工具函数和接口。例如，跨操作数约束由负责该语义的 verifier 表达，lowering 可以依赖其入口已保证的不变量。若独立入口也须验证，复用同一规则定义。
- **突出调用方必须知道的约束。** 用项目已有术语命名，在类型、签名或接口说明中明确输入输出及相关不变量、前置条件、失败和副作用。调用方需要据此决策的 shape、地址空间、Pass 顺序或适用 target 应容易查到。
- **让接口适度通用。** 实现覆盖当前需求，接口表达本层的基本语义。优先选择能自然覆盖当前场景的少量核心操作。将 CLI 用法和特定 target 的策略留在各自负责的层，避免为假设中的用例预留扩展点。
- **按职责下沉复杂性。** 将与模块职责相关、能同时简化接口和调用代码的处理放进该模块。由模块推导能够可靠确定的值。调用方拥有决定所需的信息时才暴露配置，语义允许时给出合理默认值。
- **按知识和抽象拆合。** 将依赖同一项知识的逻辑放在一起，能独立理解和使用的子任务可拆开。新增层应提供不同的抽象或明确的分发、兼容职责。必要的上下文依赖要保持显式。
- **简化边界语义，保留重要失败。** 在契约允许时，将已满足目标的情形纳入正常路径。按 MLIR 约定处理改写模式未匹配的情况。可完整恢复的失败由负责模块处理，其余交给有足够上下文的边界统一处理或报告，并保留影响调用者判断的诊断。

## 实施流程

1. **界定行为。** 从用户入口、现有测试和规范确定期望行为、影响范围及兼容要求。缺陷修复先尽量缩小为 IR 或 Python 输入、调用命令、预期和实际结果。阅读将修改的文件头和附近实现。
2. **选择改法。** 契约清晰、易回退的局部改动沿现有结构直接实施。新增或改变跨层契约、Pass 职责或依赖关系，以及难回退的结构变更，先写简短的接口契约说明，必要时勾勒签名，再比较至少两个有实质差异的可行方案。若讲清接口需要反复解释内部顺序或特例，先检查抽象。按调用方须知、依赖范围、兼容性和验证成本作选择，保留简短理由即可。
3. **按契约实现。** 经由正常入口接入改动，同步受影响的 ODS、verifier、lowering、CLI、绑定、文档和测试。若现有结构让新需求只能靠重复特判接入，先检查能否在受影响的模块内调整职责或归并规则。随代码更新契约说明，将维护者需要的设计理由写在相关定义或实现附近。
4. **验证行为。** 使用现有测试入口覆盖关键成功和失败路径，优先复用已有断言。新增行为或复现缺口需要有针对性的回归证据。IR、诊断和生成结构可用 lit 验证。涉及数值、ABI 或设备行为时，选择能直接验证该行为的相应运行测试。按仓库约定优先用 WSL 执行 PTOAS 工具链。
5. **按需测量性能。** 为提速而改动时，先测量基线、定位瓶颈，再在可比输入和目标环境下复测。仅当实测收益支持取舍时，保留为提速引入的额外复杂性。

## 评审门禁

将定位、触发条件和实际影响写进发现，优先解决当前变更引入的问题。以下情况阻断通过。

- 正常入口行为偏离需求，已有调用或输入出现未经约定的兼容性破坏，或缺少影响正确调用或排障的约束、失败语义及诊断。
- 同一语义出现会漂移的重复来源，新增隐含的 Pass 顺序或 target 假设，或受影响层之间的定义、验证和消费行为不一致。
- 本变更导致相关验证失败，关键行为缺少足以支持结论的证据，或仓库已有的适用合规门禁未通过。

浅包装、参数透传、频繁阅读跳转和难以说清的契约是追查线索。结合它们实际增加的依赖、调用负担和修改范围判断是否阻断。无关历史问题可单独记录。

## 例外

兼容旧接口、紧急修复或实测性能约束可能需要保留特例。将特例限制在最小责任边界，记录约束、受影响范围和已做验证。如属临时方案，写明收敛或移除条件。适用的正确性、兼容性和仓库门禁仍须满足。

环境缺失时，记录未能运行的命令、原因、实际取得的替代证据和剩余风险。若关键行为仍缺少证据，将对应门禁标为待验证。

## 完成标准

- 需求可通过正常入口验证，相关契约与受影响层一致，调用者所需的约束和失败行为清晰可查。
- 关键行为有足够的验证证据，适用的阻断项已解决。若仍有阻断项，交付说明应标明未通过及原因。
- 交付说明简述改动、关键取舍（如有）、验证命令及结果，以及仍存在的限制或风险。

设计原则参考 John Ousterhout 的[《软件设计的哲学（第二版）》](https://yingang.github.io/aposd2e-zh/)。
